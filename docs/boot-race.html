Time to running

How long from asking for compute to a workload answering a request, for an fcvm VM restored from a snapshot and for the usual ways of starting the same workload on AWS. Every lane runs the same program and ends at the same event: an HTTP GET from outside the VM, instance, task or function reads its complete answer.

Each ball is one lane. One round trip is one measured sample: out and back takes that sample's time, at the speed chosen above, on the same linear scale for every lane. Trips replay the lane's samples in the order they were taken; a lane that runs out starts again from its first sample and says so. The label under a lane is the trip that last landed.

Median of the successful samples; p95 is the nearest-rank 95th percentile and p99 the 99th, which with fewer than 100 samples is the slowest one. A failed sample is a run that did not answer within its deadline or whose API call was refused; it is counted here and left out of the times. So is a sample whose answer came from the wrong process (an identity check below).

Where each lane starts the clock

    One campaign, interleaved

    Every sample by the time it started (a hollow mark is a failed attempt). Each round ran every lane once, one after another, and the order rotated by one lane per round, so no lane always ran first or last.

    What each lane checks

    Setup

    Method

    • t0 is read immediately before the call that asks for compute; t1 when the probe has read a complete 200 answer. For the probed lanes t1 is taken after the answer's JSON is parsed and checked; for Lambda, right after the body is read. Teardown (terminating, stopping, killing the VM) happens after t1 and is not timed.
    • The probe runs on the campaign host. For the EC2 and ECS lanes it opens a new connection to the workload's private address every 20 ms (5 ms for ECS on EC2), until one answers; the connect, the read of the answer's head and the read of its body each have a 1 s timeout. For the fcvm lanes it does the same every 1 ms to the VM's published port, with 0.5 s timeouts. Lambda is one HTTPS request to the function URL, signed before t0, so its time includes the TLS handshake.
    • The workload is one static binary: it counts the primes below 200,000 (about half a millisecond) and returns that with a random id drawn at process start and the kernel's boot id. Those two ids are how the page tells a new process and a new kernel from a reused one.
    Source: bench/boot-race/ in ejc3/fcvm (the driver race.py, the workload, and render.py, which built this page from the campaign's records).
