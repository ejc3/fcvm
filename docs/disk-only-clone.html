TL;DR

fcvm's existing snapshot commands clone a running VM's memory + disk and resume it mid-execution via a UFFD page server. Disk-only clone captures only the disk at a consistent point and cold-boots brand-new VMs from it — no memory image, no UFFD, no shared state. Each clone is a fully independent machine that boots its kernel from scratch and re-launches the container against the prepared filesystem.

# capture only the disk of a running VM (frozen briefly for a consistent reflink; vCPUs never paused)
fcvm snapshot create --pid <vm_pid> --tag base --disk-only

# cold-boot independent copies — memory/cpu/hugepages chosen freely at run time
fcvm snapshot run --tag base --name c1 --hugepages --memory 8192 --cpu 4
fcvm snapshot run --tag base --name c2          # another fresh, independent copy

Proposed CLI. This work introduces --disk-only on snapshot create and promotes --tag + --memory/--cpu/--hugepages/--env onto snapshot run (today's run uses --snapshot with cpu/mem internal-only — see P4).

The headline architectural finding: this feature already exists as the empty cell of a 2×2 matrix. The cold-boot path and the snapshot-restore path already share the same disk-reflink machinery (DiskManager::create_cow_disk). Disk-only clone is (captured disk) × (cold boot) — a combination the current code never wires up, but whose disk plumbing is already built and tested. The design's job is to make that matrix explicit (and add the guest-side Preserve policy) instead of adding a fourth ad-hoc path.

Review provenance: this design was hardened by repeated adversarial passes (local codex + a fan-out /code-review workflow) before any code was written. Early passes caught four would-be data-loss / broken-build bugs — missing guest quiescing, an unmodeled container-state collision, ungated image resolution, and an over-broad overlay rejection. A later codex pass (gpt-5.5, re-verified against current main) caught five more, all now folded in: the container-restart mechanism (podman start --attach, not bare start), disk-resident env secrets, an unimplementable unfreeze-on-resume-failure guarantee, an over-broad freeze scope (FUSE/NFS), and clone-identity collisions (machine-id / SSH host keys). Findings and fixes are flagged inline with (codex-flagged).

The problem & the two asks

From #625, verbatim:

“i want functionality that can clone a vm but not its memory state … get a vm booted and then we clone the disk and then can start fresh copies from that cloned disk state.”

“i want the ability to start that fresh clone with huge tb's even if the original one wasnt started that way.” (huge tb's = hugepages / huge-TLB memory)

Why this is useful

Boot a VM, do expensive one-time work inside it — install packages, warm an image cache, seed a database, run a build — then capture the disk once and fan out N cold copies that each start from that prepared state. Unlike a memory clone, the copies are not frozen mid-execution: they boot fresh, so they get different resources (memory / cpu / hugepages — always free, see below) and have no shared memory pages or in-flight state to corrupt. By default each copy replays the captured container (its exact entrypoint, env, and writable layer); running a different command or supplying new env is the opt-in FreshContainer mode (C3).

The second ask falls out for free

“Start the clone with hugepages even if the original wasn't” is hard for a memory clone: Firecracker rejects the file-backed memory backend for hugepage snapshots, so hugepages force the UFFD restore path and the backing must match the snapshot (src/commands/snapshot.rs:1001, 1016). A disk-only clone has no memory image to restore, so that entire constraint evaporates — the clone allocates fresh guest RAM and can request --hugepages, any --memory, any --cpu with zero coupling to the source. See Hugepages.

The proper abstraction

Today there are two boot paths that look unrelated but in fact share their disk plumbing and differ along exactly two orthogonal axes. The design makes those axes first-class instead of bolting on a third special case.

Axis A — RootfsSource: where does rootfs.raw come from?

DiskManager::new(vm_id, base_rootfs, vm_dir) reflinks whatever base_rootfs points at into the per-VM rootfs.raw (src/storage/disk.rs:26,41). It is already source-agnostic:

  • BaseLayer — the content-addressed layer2-{sha}.raw from ensure_rootfs(...) (prepare_vm, src/commands/podman/mod.rs:297). Used by podman run.
  • CapturedDisk(path) — a snapshot's disk.raw. Already used today by snapshot-restore, which calls DiskManager::new(vm_id, restore_config.source_disk_path, vm_dir) (src/commands/common.rs:886).

Axis B — BootMode: how does the guest come up?

  • ColdBoot — fresh kernel boot; fc-agent reads the MMDS boot-plan and launches the container.
  • MemoryRestore { uffd, vmstate } — resume a paused process from a memory image.

Both occupied cells already share create_cow_disk. Disk-only clone = the existing CapturedDisk reflink (from the UFFD cell) composed with the existing ColdBoot machinery (from the podman run cell). The plumbing is reuse; the genuinely new work is the guest-side Preserve behavior — skipping the destroyers, restarting the captured container correctly, clearing stale runtime state, and regenerating identity — detailed in fc-agent.

Axis C — the policies the matrix exposes

Placing the empty cell next to its neighbours shows a disk-only clone is not just “cold boot with a different disk.” A CapturedDisk carries the whole guest state, and the matrix exposes one capture-side policy — how to copy that state consistently — and three boot-side policies — how to treat what it carries. The three boot-side policies have the same shape: for each category of captured state, choose Preserve (keep what the source built) or Fresh (regenerate it). Their defaults encode the feature's whole point in one line — preserve the work, regenerate the identity — and splitting them out this way is what an adversarial pass forced: collapsing them into one coarse policy hid two data-loss bugs.

C1 · QuiescePolicy (capture side)

What state must be flushed to the disk before the reflink. A memory snapshot is consistent only because it also captures the dirty page cache; a disk-only capture has no such safety net, so it must fsfreeze (or stop the workload) first. Detailed in the capture path.

The boot side — three Preserve-vs-Fresh choices, one per category of captured guest state. Each policy carries two defaults: its #[serde(default)] equals today's behavior so every existing plan deserializes unchanged, and the DiskOnly dispatcher explicitly sets the clone value. The clone values are the rule — preserve the work (storage → Preserve, container → StartCaptured), regenerate the identity (→ Regenerate) — while the serde defaults stay on today's path (storage Provision, container plain podman run, identity Preserve).

C2 · StoragePolicy — the podman image / layer store

On a normal cold boot fc-agent provisions storage — it wipes podman state and (re)installs the image. On a disk-only cold boot the storage is already prepared inside the captured disk, so fc-agent must preserve it:

StoragePolicyUsed byfc-agent behavior
Provision (default)BaseLayer cold bootwipe storage, set up storage.conf, load/pull the image
PreserveCapturedDisk cold bootkeep captured storage; skip every reset + the destructive btrfs setup; verify image present; re-attach a read-only store only if one existed

C3 · ContainerStatePolicy — the container & its writable layer

The subtlety an adversarial review surfaced: fc-agent always issues podman run --name fcvm-container with no --replace (fc-agent/src/container.rs:948). A captured VM already has an fcvm-container record and writable layer, so a naïve re-run either collides on the name or, if pre-removed, deletes the prepared layer. The clone must choose explicitly:

ContainerStatePolicySemanticsPreserves writable layer?
RunNew (#[serde(default)])today's plain podman run --name fcvm-container — the back-compat default; on a normal boot there is no captured container to worry aboutn/a (no captured layer)
StartCaptured (clone default)podman start --attach the captured container — replays its exact entrypoint + env against its exact writable layer; no name collision (it's a start, not a run). Cmd/env are fixed at capture and cannot be overridden hereyes
FreshContainerremove the captured record, podman run a new one — keeps the image + volumes, discards the old container's writable layerno (image + volumes survive)

The #[serde(default)] is RunNew (today's behavior), so existing plans are unchanged; the DiskOnly dispatcher explicitly selects StartCaptured (clone default) or FreshContainer.

v1 defaults to StartCaptured: it is the most faithful reading of “start fresh copies from that cloned disk state” — everything written inside the source (including the container's own filesystem) reappears in each copy — and it sidesteps the name collision because podman start fcvm-container resumes the existing record rather than creating a duplicate.

The restart mechanism must replace the attached-run model (codex-flagged). fc-agent today launches the container with an attached podman run: it spawn()s podman as a child, pipes its stdout/stderr, child.wait()s for the exit code, then podman rm -fs it (container.rs:950 run, :1271–1274 spawn+pipe, :1314 wait, :1341–1348 cleanup). A bare podman start returns immediately — no child to wait on, no pipes — so it would break exit-code / output / TTY forwarding. StartCaptured must therefore use podman start --attach (plus -i when interactive), which attaches stdout/stderr/stdin and blocks until the container exits, fitting the existing spawn→pipe→wait model. The captured container's saved state is running at capture time (a record from another boot whose runtime is gone), so the recovery transition must be concrete: podman container cleanup fcvm-container (resets runtime state Running→Exited) → assert it is not actually running → podman start --attach, failing closed on any unexpected state. This reconciliation must finish before health checks can inspect the container: fc-agent's exec server comes up early (agent.rs:114) and the health monitor marks healthy on the container's .State.Running (src/health.rs), so the stale captured Running record would otherwise read false-healthy before the clone's container is actually up — gate health/exec visibility on a clone-boot readiness marker. The attached-run model has distinct TTY (container.rs:1248) and non-TTY (container.rs:1271–1314) paths that StartCaptured must both cover. (After the clone's container exits, fc-agent podman rm -fs it in non-TTY mode — container.rs:1338 — but TTY mode powers off without removing — container.rs:1247 — so a TTY run leaves the captured layer in place; StartCaptured must handle both consistently.)

Overrides require FreshContainer (codex-flagged). Because podman start replays the captured record, it cannot change the container command or env — those were baked at the source's podman run -e (container.rs:1012). So running a different command or supplying --env requires explicitly selecting FreshContainer (keeps image + volumes, fresh writable layer); under the StartCaptured default these overrides are rejected with a clear error that points to FreshContainer — never a silent policy switch (which would discard the writable layer) and never a silently-ignored override. VM-level resources (memory / cpu / hugepages) are orthogonal and free under both modes. The P4 “file written inside the container layer survives” test exercises the StartCaptured default.

C4 · IdentityPolicy — machine-id, SSH host keys, hostname

The one category whose clone default flips to Fresh: N copies of one disk must not share a system identity. So where storage and container default to Preserve (keep the work), identity defaults to Regenerate — the “regenerate the identity” half of the rule. This is the symmetry that makes the abstraction click: same Preserve-vs-Fresh shape, opposite default, because identity is the one captured thing a clone must not inherit.

IdentityPolicySemanticsClone default?
Regenerate (clone default)in the initrd, before switch_root (gated by a kernel-cmdline flag — the initrd can't read MMDS): clear /etc/machine-id + /var/lib/dbus/machine-id, and SSH host keys if openssh-server is present; per-clone hostname via a new MMDS field. MAC + DNS are already per-clone-fresh (generate_mac, configure_dns_from_cmdline)yes
Preserve (#[serde(default)])keep the captured identity — matches today's single-VM behavior, so old plans are unchanged. Wrong for clones: would collide machine-ids / host keysno

Why initrd and not fc-agent: by the time fc-agent.service runs, systemd has already cached the machine-id and sshd may have presented captured host keys — the layer detail is in fc-agent. Note IdentityPolicy governs only the VM/guest identity; the container's own identity is part of the captured workload and is intentionally preserved under StartCaptured.

Why exactly these three categories — and not journald, chronyd, networkd, the package DB, /run…? Because a disk-only clone is a cold boot from a crash-consistent disk (that is what the fsfreeze in QuiescePolicy guarantees). So every stateful guest daemon recovers exactly as it would after a power-cut reboot of the source: journald rotates its journal, chronyd re-reads its drift file and re-syncs, systemd-networkd + /etc/resolv.conf are rebuilt from the boot args, /run is a fresh tmpfs, the apt/dpkg DB is simply the installed set. None of that needs a policy — a normal boot already handles it. The three boot-side policies are precisely the deltas from a normal reboot — the three things a clean reboot of this disk would get wrong: fc-agent would wipe the captured store (→ StoragePolicy), the captured container record would collide / lose its layer (→ ContainerStatePolicy), and every copy would share one identity (→ IdentityPolicy). That framing is what makes the partition closed: capture a consistent disk, then fix only what a reboot can't.

The boot-side policies surface on the wire as a few #[serde(default)] fields whose defaults equal today's behavior, so every existing plan deserializes unchanged — StoragePolicy/ContainerStatePolicy on the MMDS Plan, and IdentityPolicy::Regenerate as a kernel-cmdline flag read by the initrd. This is where the feature can destroy data if done wrong — see fc-agent and Risks.

Why this is the “proper” abstraction, not a fourth path: it names the two axes the code already varies along (RootfsSource × BootMode), places all three real boot scenarios in one matrix, and factors the genuinely new behavior into defaulted policies of one repeating shape — a capture-side quiesce plus three boot-side Preserve-vs-Fresh choices over the categories of captured state (storage, container, identity) — instead of one ad-hoc branch. No existing path is special-cased; the disk-only clone is a composition plus those explicit, symmetric choices. It also lines up with the planned hypervisor abstraction — RootfsSource/BootMode map onto its neutral RestoreSource/SnapshotKind types, and cold-boot-from-disk is VMM-agnostic (both Firecracker and Cloud Hypervisor do direct kernel boot).

fc-agent: the Preserve storage policy

On a normal boot the guest agent destroys podman storage and rebuilds it. A disk-only clone must not — the captured disk already contains the writable container layer and (for some image modes) the image itself. This is the highest-risk part of the feature.

The wipe risk (line citations point at the command, not the comment/signature). There are four reachable destroyers: podman system reset --force at container.rs:452–454 (reset_podman_state, root), :426–428 (btrfs setup), :68–70 (after storage.conf), and a reset inside create_vm_user at container.rs:1115–1118 (called from agent.rs:225) when a non-root --user is set. And the btrfs setup is destructive even before its reset: it truncates /var/lib/containers/btrfs.img (container.rs:358) and runs mkfs.btrfs -f (container.rs:377), reached via agent.rs:189 for non-overlay modes. A Preserve boot must skip all of these, not just the resets.

On the wire this is #[serde(default)] storage_policy/container_state_policy fields on the Plan struct (fc-agent/src/types.rs), defaulting to today's behavior — so existing plans deserialize unchanged (proven by the minimal-plan test). Changing fc-agent requires rebuilding the initrd (content-addressed by the fc-agent binary SHA).

Subtlety codex's second pass caught — Preserve ≠ "skip the btrfs branch entirely". On a non-native-btrfs rootfs the image store is a loopback at /var/lib/containers/btrfs.img that is created+formatted+mounted at boot (container.rs:328/358/377/396). The file is reflinked (it's inside rootfs.raw), but the loopback mount does not survive a cold boot. So Preserve must skip only the destructive steps (truncate + mkfs) while still mounting the existing btrfs.img — otherwise a btrfs/archive clone boots with the image present on disk but not mounted, i.e. invisible to podman.

Two things the clone boot must actively DO, not just skip

Most of StoragePolicy::Preserve is about not destroying captured state — but two cold-boot hazards need positive action: one belongs to StoragePolicy::Preserve (runtime-lock cleanup), the other is IdentityPolicy::Regenerate (both codex-flagged):

  • Clear stale runtime locks (only) — NOT container/image metadata. The source was captured with a running container, so /var/lib/containers carries live runtime records. Preserve skips the destructive reset, so it must instead do a tight, allow-listed cleanup: delete only the stale lock files (storage.lock, userns.lock) and transient conmon/pid + run-root state so podman start reconciles. It must not touch db.sql (the storage DB stays valid because Preserve keeps the captured storage.conf, so the graph driver still matches) and must not delete libpod/, overlay-containers/, or overlay-images/ — those hold the captured container & image. The base-rootfs build removes that whole set (rootfs.rs:684), but only because it runs on an empty rootfs; Preserve reuses just the lock subset. This is the precise line between “runtime locks” (safe to clear) and “persistent metadata” (must preserve).
  • Regenerate guest identity — machine-id & SSH keys in the initrd. Every clone boots the same disk, so they share /etc/machine-id, SSH host keys, and hostname unless regenerated. The machine-id and SSH host-key removal must happen in the initrd init script before switch_root (rootfs.rs:1375) — not in fc-agent.service, which starts after systemd has cached the machine-id and after sshd may have presented captured host keys (rootfs.rs:1220). The initrd can't read MMDS (it parses only /proc/cmdline, rootfs.rs:1276), so this is gated by a kernel-cmdline flag (like the existing fc_agent_strace) and needs no external data: delete /etc/machine-id + /var/lib/dbus/machine-id (systemd re-seeds machine-id on boot), and for SSH remove the host keys and run ssh-keygen -A chrooted into /newroot when openssh-server is present (not in the base rootfs package lists, rootfs-config.toml:67–79) — regenerating in the initrd rather than relying on a later service. The per-clone hostname is set later by fc-agent via a new MMDS field (today only WWW_HOSTNAME, agent.rs:344; MMDS has no hostname field yet, src/firecracker/config.rs:368). MAC and DNS are already per-clone-safe — fresh generate_mac() (network/types.rs:124) and configure_dns_from_cmdline() rewrites resolv.conf (fc-agent/src/network.rs:279) — so only machine-id / SSH keys / hostname need handling. Clear both /etc/machine-id and /var/lib/dbus/machine-id (if present) plus SSH host keys. This is VM-level identity only — the captured container's own machine-id / SSH keys are intentionally preserved under StartCaptured (faithful replay); FreshContainer is the path to a clean container identity. Otherwise duplicate machine-ids break systemd / journald / DHCP-DUID and duplicate host keys trip SSH known-hosts.

The image-delivery wrinkle (refined after review)

The first draft said “reject overlay mode.” An adversarial pass showed that conflates two different things — what matters is where the image physically lives, which is determined by delivery, not the image_mode label:

How the source got its imageWhere the image livesDisk-only capture
Remote pull (image_mode=None, no device) — fc-agent pulls into rootfs at boot (agent.rs:264)baked into rootfs.raw✓ works — reflink carries it
btrfs / archive — fc-agent podman loads into rootfs storagebaked into rootfs.raw✓ works
localhost overlay — RO .storage-v2.img attached as additionalImageStore (mod.rs:541)separate content-addressed device, NOT in rootfsv1 reject / v2 re-attach

So the v1 guard must key on the effective delivery — “was a separate read-only overlay store device attached?” — which is exactly what MMDS records: it emits image_mode only alongside an image_device (src/firecracker/config.rs:377–378). It must not key on the raw resolve_image_mode(), which defaults to Overlay even for remote pulls (mod.rs:77) that have no device and bake into the rootfs; and not on “an image_device exists,” because btrfs/archive also attach a device (vm_config.rs:481) yet podman load it into the rootfs. The reject condition is precisely overlay-mode AND a store device was attached. In every mode the container's writable layer lives in /var/lib/containers on rootfs.raw; that is what Preserve + ContainerStatePolicy protect.

v1 — rootfs-baked images

Remote-pull, btrfs, and archive: the image is in the reflinked rootfs; Preserve skips the wipe and runs from local storage. Only the separate-store localhost-overlay capture is rejected (clear error). Smallest, safest first cut.

v2 — overlay re-attach

Record image_mode + digest; on cold boot re-attach the same content-addressed .storage device (shared, always present) exactly like a normal overlay boot, then Preserve keeps the writable layer. No baking needed.

The capture path

Disk-only capture is create_snapshot_core (src/commands/common.rs:1553) with the memory half removed and a guest quiesce added. The factored create_disk_only_snapshot_core drops the vCPU pause/resume bracket entirely — fsfreeze provides filesystem consistency, and disk-only skips the Firecracker create_snapshot call that was the only operation requiring Paused. Keeping vCPUs live throughout is what makes the unfreeze and the auto-thaw watchdog (below) actually work.

Consistency comes from the freeze, not a pause (corrected after review). The memory-snapshot flow pauses vCPUs to dump the dirty guest page cache into memory.bin (common.rs:1696). Disk-only has no memory dump, so a vCPU pause alone (common.rs:1683) would buy nothing — it would still leave un-written-back dirty pages and in-flight journal state out of rootfs.raw, capturing a torn filesystem. So disk-only skips the pause entirely and instead quiesces the guest with fsfreeze, which flushes and blocks writes — the actual consistency guarantee.

QuiescePolicy — flush the guest before the reflink

Before reflinking, fcvm runs a quiesce command inside the guest over the existing exec vsock channel — the same path fcvm exec uses (host src/commands/exec.rs:146 → fc-agent exec server agent.rs:120 → guest command fc-agent/src/exec.rs:377). No new control channel is needed, and because it's a runtime command (not the boot-time Plan), capture can use it without any fc-agent build change.

LevelAction in guestGuarantee
Syncsync(2)best-effort only — a write window remains between sync and the reflink, so not race-free on its own
Freeze (the correctness floor)fsfreeze --freeze each captured block filesystem — rootfs, the nested btrfs.img loopback at /var/lib/containers/storage (container.rs:396), and block extra disks; not FUSE / NFS / tmpfs / proc — deepest-first → reflink → fsfreeze --unfreeze in reverse ordercaptured filesystems are crash-consistent and no writes can land across the reflink
StopContainerstop the workload, then freezestrongest: also drains userspace buffers (needed if the app buffers writes itself)

Ordering: freeze (exec vsock) → reflink → unfreeze (exec vsock) — no vCPU pause. Freeze is the floor because Sync alone leaves a window before the reflink. This is the gap codex's first review flagged ("needs disk quiescing").

Unfreeze no longer depends on a Firecracker resume (no pause = no wedge). Because disk-only never pauses, vCPUs run throughout, so fsfreeze --unfreeze over the exec vsock does not depend on a resume succeeding — the memory flow's “resume failure” wedge (common.rs:1813) simply doesn't apply here. (codex-flagged) An exec can still fail if the guest is otherwise unhealthy, which is exactly the capture-process / guest-death case handled next.

Process death mid-freeze must self-heal (codex-flagged). If the fcvm capture process is SIGKILLed / panics between fsfreeze --freeze and unfreeze, nothing host-side is left to thaw. Two independent safeties: (1) a host scope-guard that unfreezes on panic / early-return, and (2) a guest-side auto-thaw deadline armed before the freeze — the quiesce helper schedules a detached guest timer (e.g. systemd-run --on-active=Ns -- fsfreeze --unfreeze <mounts>) that fires if the host never returns. Because vCPUs are never paused, this timer actually runs — it could not if the guest were paused, which is the deeper reason disk-only drops the pause. On success the host cancels the timer and unfreezes in reverse order; a longer copy re-arms a fresh deadline; auto-thaw is idempotent — a duplicate unfreeze is treated as success (fsfreeze --unfreeze returns an error when the FS is already thawed, which the caller must swallow). Regression tests must cover reflink failure, cancellation, and host SIGKILL / panic mid-freeze. Per the repo's ZERO-RACE rule, a frozen source must never depend on one host process staying alive.

Env in the host state file is not persisted — but the captured disk still carries the container's env (codex-flagged). fcvm omits env from the world-readable host state file (mod.rs:613–614, types.rs:109; perms set at manager.rs:144). However the source container was launched with podman run -e KEY=VAL (container.rs:1012), so those values live in the container config under /var/lib/containers on rootfs.raw — which the reflink does capture. A disk-only snapshot is therefore as sensitive as its source container's env: treat the snapshot directory as secret-bearing, and do not pass secrets as --env to a container you intend to capture (mount them instead). The new --env on snapshot run only adds new env for a FreshContainer clone — it does not, and cannot, scrub env already baked into the captured container under StartCaptured.

Hugepages & resources come free

The second ask — “start the clone with hugepages even if the original wasn't” — needs no new mechanism. It is purely a consequence of cold-booting.

Memory clone (constrained)

Hugepages force the UFFD restore path; Firecracker rejects the file backend for hugepage snapshots, and the backing must match what was captured.

// src/commands/snapshot.rs:1016
if hugepages || env("FCVM_FORCE_UFFD") {
    // implicit in-process UFFD server …
}

Disk-only clone (free)

No memory image ⇒ no backing to match. The cold-boot path already feeds args straight into the machine config:

// src/commands/podman/vm_config.rs:927
MachineConfig {
  vcpu_count: args.cpu,
  mem_size_mib: args.mem,
  huge_pages: if args.hugepages { Some("2M") } else { None },
}

--hugepages, --memory, and --cpu are already implemented for the fresh-boot path; the disk-only run just exposes them on snapshot run and lets them flow through unchanged. The only existing guard that still applies is the 2 MiB memory-alignment check for hugepages (mod.rs:162).

Top risks & mitigations

Ranked; the first three are data-loss / silent-corruption class and gate the design.

  1. Torn filesystem — a reflink without quiescing captures dirty/in-flight state. (codex-flagged) Without a memory snapshot, dirty guest pages never reach the disk (and a vCPU pause wouldn't flush them either). Mitigation: QuiescePolicy — sync/fsfreeze (or stop the workload) before the reflink; freeze brackets the copy.
  2. fc-agent destroys the captured storage. Four resets plus a truncate+mkfs btrfs setup plus create_vm_user's groupadd/useradd and /etc/subuid,/etc/subgid truncation ((codex-flagged) container.rs:1079–1095) for a non-root --user. Mitigation: StoragePolicy::Preserve guards all of them (container.rs:452/426/68 + 358/377), and uses a non-destructive ensure-user path (no subuid/subgid rewrite) or v1 rejects capturing a non-root --user VM; Provision stays the default. Covered by the “file inside the container layer survives the clone” e2e test.
  3. Container name collision / writable-layer loss. (codex-flagged) podman run --name fcvm-container has no --replace. Mitigation: ContainerStatePolicy — v1 StartCaptured (podman start --attach, preserves the writable layer, no collision); FreshContainer opt-in.
  4. Clone needs the original host image tag. (codex-flagged) prepare_vm always resolves/exports the image. Mitigation: gate image-resolution + localhost-export (mod.rs:320,451) on rootfs_override — a rootfs-baked clone needs neither.
  5. Separate-store (localhost-overlay) image not in the rootfs. Mitigation: v1 rejects only when a separate read-only overlay store device was actually attached (the effective delivery, recorded in metadata) — never the raw resolve_image_mode(), which defaults to Overlay even for remote pulls that bake into the rootfs; v2 re-attaches the content-addressed store.
  6. Boot-plan drift — wrong kernel or VMM args for the source. (codex-flagged) Mitigation: persist the effective boot config in metadata — kernel_profile + explicit --kernel, plus firecracker_args/boot_args/fuse_readers/binary selection (or a config digest) — and cold-boot under it; rootfs_type alone is insufficient.
  7. Secrets baked into the captured disk. (codex-flagged) Host state omits env, but podman run -e bakes the source container's env into /var/lib/containers on rootfs.raw, which the reflink captures. Mitigation: treat disk-only snapshots as secret-bearing; don't pass secrets as --env to a container you will capture (mount them); --env on snapshot run adds new env only for FreshContainer.
  8. Container restart breaks I/O forwarding. (codex-flagged) fc-agent's attached podman run spawns + waits + pipes (container.rs:1271–1314); a bare podman start returns immediately. Mitigation: StartCaptured uses podman start --attach (+ -i when interactive), fitting the spawn→pipe→wait model.
  9. False-healthy from the stale captured container. (codex-flagged) The health monitor marks healthy on fcvm-container's .State.Running, and the captured record is stale-Running — so a clone could read healthy before StartCaptured actually re-runs it. Mitigation: complete podman container cleanup → start --attach before exec/health can observe the container (gate on a clone-boot readiness marker).
  10. Stale podman runtime state survives Preserve — but over-cleaning destroys the container. (codex-flagged) A captured running container leaves stale lock files (storage.lock, userns.lock, conmon/pid). Mitigation: Preserve does a tight, allow-listed cleanup of only those locks before podman start — it must not delete db.sql/libpod/overlay-containers/overlay-images (the captured container + image); the base build (rootfs.rs:684) removes that whole set only because the rootfs is empty.
  11. Clone identity collisions. (codex-flagged) N copies of one disk share /etc/machine-id, SSH host keys, and hostname; nothing regenerates them today (hostname only on WWW_HOSTNAME, agent.rs:344). MAC + DNS are already per-clone-safe (generate_mac, configure_dns_from_cmdline), so only machine-id/SSH/hostname remain. Mitigation: rm /etc/machine-id + SSH host keys in the initrd before switch_root, gated by a kernel-cmdline flag (the initrd can't read MMDS); set the per-clone hostname later via fc-agent's MMDS path.
  12. Wrong fsfreeze scope (both directions). (codex-flagged) Freezing host-served FUSE/NFS mounts can hang while the guest is frozen (vsock/network round-trips can't complete); conversely, freezing only / misses the nested btrfs.img loopback (container.rs:396) and captures a torn image store. Mitigation: freeze exactly the captured block filesystems — rootfs + the btrfs.img loopback + block extra disks, deepest-first — and skip FUSE/NFS/tmpfs.
  13. Capture process dies while the guest is frozen. (codex-flagged) A SIGKILL/panic after fsfreeze --freeze but before unfreeze leaves the source wedged. Mitigation: a scope-guard that unfreezes on panic/early-return and a guest-side auto-thaw deadline so a dead host self-heals (ZERO-RACE: never depend on one host process surviving).
  14. External --disk paths aren't reconstructible. (codex-flagged) Only --disk-dir images are copied into the snapshot (common.rs:1433); external --disk paths are filtered out and not stored in SnapshotMetadata at all (snapshot.rs:66), so a clone has no reference to re-attach them — and they're invisible from metadata, so the guard must read VmState.config.extra_disks directly. Mitigation: disk-only inherits the existing rw-extra-disk rejection (snapshot.rs:104) and additionally rejects any external --disk (detected from VmState) at capture (clear error); v2 may persist + re-attach read-only external disks (writable shared disks stay rejected — they'd break clone independence).
  15. Footgun: --pid (UFFD) on a DiskOnly tag. Mitigation: dispatch rejects it; a DiskOnly tag has no memory image to serve.

Fit with the hypervisor abstraction

fcvm has a separate RFC to become hypervisor-agnostic (Firecracker + Cloud Hypervisor — docs/hypervisor-abstraction.md, epic #632). Disk-only clone is designed to land now on the Firecracker path while mapping cleanly onto those future neutral types:

Disk-only conceptHypervisor-abstraction neutral type
RootfsSource::CapturedDiskRestoreSource (VMM-neutral; reflink/bind-mount redirect is already VMM-agnostic)
SnapshotKind::DiskOnlySnapshotKind (the doc already plans Full vs diff; DiskOnly is a third, memory-less kind)
BootMode::ColdBootthe trait's configure+start (direct kernel boot — supported by both FC and CH)
StoragePolicy (guest)part of the VMM-neutral boot-plan over vsock (guest channel is byte-identical across backends)

Because a disk-only clone needs no snapshot format, UFFD, or drive-retarget — the three things that differ most between Firecracker and Cloud Hypervisor — it is the most portable clone variant and a natural early win for the CH backend (which the RFC schedules as “P1: cold boot + run a container, no snapshots”).
