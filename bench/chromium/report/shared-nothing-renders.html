Shared-Nothing Renders

fcvm runs each browser-render request in its own Firecracker microVM: restored from a snapshot of an already-running Chromium, driven over the Chrome DevTools Protocol, destroyed after one page. This report measures what that costs, on one Graviton3 server. Each number cites the run that produced it.

What a render actually demands, instant by instant

Everything above measures averages, and an average cannot answer whether a guest has enough vCPUs. A 2-vCPU guest can never exceed 2.0 instantaneous cores, so its average is taken under a ceiling: 1.5 cores of a 2-core budget is equally consistent with steady demand plus spare capacity, and with bursts that saturate both cores separated by idle. Those call for opposite decisions.

Each point of a ladder is one gated run of 202 requests, which is 202 samples but a single experimental unit. The confidence intervals the harness reports are within-run and do not carry run-to-run variance. Five independent bursts per configuration, with burst-level intervals, is what would let the ladder’s medians carry real error bars, and that campaign has not been run. The 2026-09-02 ladder is one burst per rung.

The service being measured

One request: restore a clone from a golden snapshot, render one page (screenshot + DOM text) through Chromium's CDP endpoint, driven from the host over a forwarded port, then destroy the clone. Requests share nothing except the read-only snapshot.RB-uffd / RB-file analysis.json arms.exec.blocking_ms.median

Terms used throughout. A golden snapshot is a saved VM image (memory, disk, device state) taken once, at a point where headless Chromium is booted, warmed up (JIT and network service exercised), and idle; every request restores a copy-on-write clone of it. copy and minor are the two userfaultfd modes the memory server uses to fill a clone's RAM on first touch: copy duplicates each faulting 4 KB page into the clone's private memory (UFFDIO_COPY); minor keeps the snapshot in a shared in-memory file and maps the existing page into the clone (UFFDIO_CONTINUE), so clones share clean pages. Hugepages backs guest RAM with 2 MB pages instead of 4 KB, 512× fewer mappings. Prefetch replay: the server records which pages previous requests touched and pre-populates them on restore, off the critical path. Runs measure up to four arms (exec is optional from the NC run onward, which schedules three): cdp (render over CDP, normal teardown), cdp-fast (same render, teardown overlapped with the response), exec (the retired in-guest driver, kept for continuity), and noop (restore, boot, and teardown with no render; the VM-lifecycle baseline, which also serves as a drift canary: its latency should be constant, and the analyzer rejects any run where it is not). Same-golden means two runs restored the identical snapshot; absolute numbers vary ~25% between goldens, so only same-golden pairs are quoted as A/B deltas. Guests are 2 vCPU / 1024 MiB unless stated.

Two workloads. The headline workload is Cloudflare's published 14-URL corpus, byte-replayed locally and rendered in the guest — the CV run, first results section below. The mechanism workload, used for every A/B and optimization comparison, is medium.html, a deterministic fixture (1.4 KB HTML, 14-rule stylesheet, 806 B of real DOM-mutating JS whose execution the DOM dump verifies, four generated PNGs ≈375 KB) served in-guest with Cache-Control: no-store, so every render re-fetches and cold-compiles everything; its byte-identical renders are what make small configuration deltas measurable. The golden's warm point renders a different document and navigates to about:blank before the snapshot; the warm page shares zero byte-resources with the measured pages (enforced by test_fixture_isolation.py). The PF, CPU, and hugepage runs use goldens with that isolation; the earlier runs predate it and carry a disclosed caveat (their warm point had preloaded the site's shared stylesheet and one image).pages/, entry.sh warm point, test_fixture_isolation.py

Three network modes, priced

Every fcvm measurement elsewhere in this report runs in rootless mode: fcvm's default, run as an ordinary user, with pasta forwarding the CDP port. fcvm has two root-only alternatives — bridged (a network namespace with veth and per-clone iptables DNAT) and routed (veth with kernel IPv6 routing, the CDP port forwarded by a built-in TCP proxy) — and either alternative costs about a fifth more end to end, most of it before and after the render. The stage rows cannot be compared naively, because "port accepts" is a different physical event in each mode. pasta and the routed proxy listen host-side and accept a connection before the restored guest can answer anything, so the guest's wake-up lands in their resolve stage as retries; bridged DNAT completes a connect only once the guest's own stack answers, which is why its resolve costs almost nothing. The rows that name the same physical work everywhere are render, screenshot, the total, and teardown; the first two rows book the same guest wake-up differently per mode.

On those rows: rootless is fastest or tied everywhere, and the two root modes each pay a small data-path tax in a different place. Routed's screenshot runs 10 ms slower than rootless (86.6 vs 76.4, disjoint intervals) — the stage that moves the largest payload, which is where relaying every CDP byte through a userspace proxy would land it (code-inferred; the relay is routed's only userspace hop). Bridged's screenshot matches rootless — its DNAT path stays in the kernel — but its navigate runs 16 ms slower (184.6 vs 168.6, disjoint intervals in this single sealed cell, not yet independently replicated) and so far unattributed: no measured mechanism explains it. The full gaps are +98 ms bridged and +99 ms routed; net of the two stage taxes above, roughly +81 and +86 ms of that is setup — per-clone veth/TAP plumbing plus iptables rule installation for bridged, namespace setup plus the proxy for routed (medians are non-additive, so these attributions are coarse). Teardown, which bounds churn and requests-per-second rather than latency, is 2.3× rootless under bridged and 1.4× under routed. Routed's headline advantage — bulk egress at kernel line rate, no userspace on the data path — cannot appear on this workload: the page is served inside the guest, and the only traffic that crosses the boundary is the CDP session. One conflation is inherent and worth naming: the two root modes cannot run unprivileged, so "bridged vs rootless" is also "root vs uid 1000"; the deltas here price the mode and its privilege model together, which is how an operator would experience them.

The comparison is stark: the same workload costs 553–611 MiB per clone on 2 MB pages and 133–146 on 4 K pages, flat through N=32. The driver is copy-on-write granularity — a write to one byte of a shared 2 MB granule privatizes all of it, and Chromium's writes are scattered — with the caveat that the granularities live in separate goldens, so golden-to-golden variation is not fully excluded. Concurrency itself adds nothing at 1 GiB: the 4 K marginal is flat from N=1 to N=32. Shrinking the guest to 768 MiB helps at low N (108–129 per clone, the best density point measured) but genuinely degrades under load — 203 MiB and 1.4 s renders at N=32, memory pressure inside the small guest — and does not help the 2 MB configuration at all (it privatizes 83–89% of the whole guest). The frontier: 2 MB pages for latency, 4 K at 1 GiB for density, 4 K at 768 MiB only for low-concurrency fleets.

An in-guest attribution run on a live 4 K clone decomposed the per-clone cost, using the Firecracker process's anonymous-memory counter (private CoW copies) beside guest /proc accounting. The clone's floor — before any render, probe-free — is ~120 MiB of genuine guest restore-time writes (network reconfiguration for the clone's new address, agent, clock, kernel housekeeping). Firecracker's own anonymous heap is 1.2 MiB, and prefetch replay adds 1.6 (its UFFDIO_CONTINUE path measured non-privatizing). The measurement tool itself is visible at this resolution: the first in-guest exec costs ~20 MiB of guest writes, and each subsequent capture ~2–3, so the render deltas below carry a few MiB of observer cost. One medium-page render then privatizes ~43 MiB. Two diagnostic controls size its components — production clones render once, so these are instruments, not workload: an identical second render adds ~16 (separating fixed page footprint, which would re-add nothing, from ongoing allocator/GC churn, which re-adds), and a heavy 1.8 s page adds ~124 (sizing the page dependence). Guest-side accounting for the first render moved only ~10–15 MiB of net new allocation (single capture); most of the 43 is the browser rewriting memory it already owned (code-inferred: GC marking, allocator churn, IPC buffers). Privatization grows with browser active time, not with page size alone — anything that shortens the render also cuts memory.

Two browser-flag experiments. Silencing Chromium's background features (metrics recording-only, no pings, domain-reliability off, a disable-features list) saves ~25 MiB of floor with renders unchanged; per-flag attribution was not isolated. Disabling V8's concurrent and incremental GC backfires: the heavy page's memory step rises from 122 to 296 MiB, because forced synchronous mark-sweep-compact writes more pages than the background marking it replaces. The default GC stays.

Two idle-time behaviors matter for interpreting any held-clone measurement, both measured directly: a just-rendered clone privatizes another ~100 MiB in its first ten idle seconds (the browser's post-load housekeeping burst), then ~10 MiB per 30 s (idleaging/ unretained, the 0–120 s curve); and repeating the identical render decays from +45 MiB to +2–5 by the tenth repetition as heap reuse overtakes frontier growth (converge/ unretained). Shared-nothing clones die at the response and pay neither. Both granularities show rare 5–7 s render stragglers that recover on their own.

A second engine: WebKit on the same substrate

The same shared-nothing design now runs WebKitGTK (webkit2gtk-driver 2.50.6-1~deb12u2; MiniBrowser under Xvfb, driven over W3C WebDriver classic — WebKit has no CDP endpoint). The engine-forcing constraint: classic WebDriver has no session discovery, so the warm session is created BEFORE the golden snapshot and every clone inherits its id. That design survives restore (foldfix/results.txt unretained): a restored clone renders on the inherited session with navigate at 64.4 ms; its first screenshot request takes 1428.9 ms and its second 87.2 — the screenshot path warms per clone rather than arriving warm from this golden's snapshot, and the report times the whole WebDriver request (protocol and PNG transfer included), not the encoder alone. First ladder (N = 1–32, 4 K minor, same accounting): restore p50 44 ms at N=1 (Chromium: 41), navigate p50 221 ms, full first render ~1.9 s — dominated by that first screenshot request; the protocol is PNG-only where CDP offers JPEG, an engine/protocol difference — and a clean N=1 marginal of 147 MiB per clone — at parity with Chromium's 146 on the matched basis (the 4 K, 1 GiB clean N=1 cell in the memory-frontier table). The Firecracker build

The benchmark binary builds from ejc3/firecracker, branch bump-vsock-max-connections: upstream main as of 2026-02-17 plus five commits, which are four changes: the serial-interrupt entry below is a fix plus its regression test. Two of the four fix bugs that upstream has since fixed independently — in both cases after, and crediting, these reports — but this binary's base predates those upstream fixes, so the fork patches remain load-bearing here. Ranked by relevance:

  • UffdMinor memory backend — guest RAM maps MAP_PRIVATE over a memfd the fcvm memory server passes across the UFFD handshake, registered for minor faults. This is what makes minor mode possible at both granularities — the 2 MB latency mode and the 4 K density mode (133–146 MiB per clone) in the concurrency table, the shared-backing amortization, and every minor-mode memory number in this report. Only copy mode works without it.
  • vsock muxer connection limit 1023 → 16384 (fork-only; not filed upstream) — every clone's status and exec channels ride vsock, and per-request clone churn burns through connections.
  • THRE serial interrupt on snapshot restore (regression test) — restored guests' serial console; diagnostics correctness, not performance. Reported upstream as #5730; upstream resolved it with maintainer-authored UART state save/restore (#5764, merged 2026-03-31, after this base).
  • dump_dirty file-cursor alignment — snapshot-writing correctness on the golden-creation path. Reported upstream as #5696; upstream shipped its own fix in v1.14.2 (2026-02-27, after this base), crediting the report.

One essential property deserves precision. Restored clones need their monotonic clock to continue from the snapshot instant, or every armed timer fires at once. The interrupt storm that makes restores look 25–300× slower (#630) requires two ingredients that exist only in this project's nested-virtualization fork: a virtual-EL2 guest whose saved register list contains CNTVOFF_EL2 (replayed after the counter registers, clobbering the kernel's offset adjustment), and NV2's trap-and-emulate EL1 timers as the re-fire amplifier. The fix — Firecracker owning the VM-wide offset via KVM_ARM_SET_COUNTER_OFFSET — lives only in that fork; upstream has never used that ioctl on any path, and the fork's upstream submission of it is prepared but not yet opened. The benchmark binary is upstream-based with no NV2 support, so neither ingredient exists: its guests are plain EL1, and what keeps their clock continuous on restore is the host kernel, not Firecracker code — since Marc Zyngier's March 2023 kvm-arm series (KVM_CAP_COUNTER_OFFSET, writable counter registers), KVM recomputes the VM-wide counter offset when snapshot restore replays the saved counter registers, so armed timers stay coherent by construction. Upstream's own use of the capability is boot-time counter reset (Egor Lazarchuk, Jan 2025), which zero-bases fresh VMs and is orthogonal to restore. Twelve gated runs of storm-free restores are consistent with this mechanism.

Bottom line

On Cloudflare's own 14-URL corpus, byte-replayed and rendered per-request-isolated in the guest on 4 guest vCPUs, the DNS-verified mix median is 549.4 ms [467.9–632.4], with per-URL medians from 326.2 ms to 2.9 s: below Kitesurf's 1,148 ms isolated-render column and below their 637 ms warm-pool column, interval included, with the network and dead-chain asymmetries stated in its section and a cold microVM per render against their reused warm browser. The DNS-verified ladder puts the knee between 2 and 4 vCPU, at 770.3, 549.4 and 580.2 ms; a second verified 2 vCPU run reads 712.6 ms [610.5–808.5]. The 2026-08-16 ladder that once put the headline at 4 vCPU is withdrawn for live-DNS contamination and none of its figures are used. On the controlled fixture, the fastest gated run of the best configuration (hugepage minor, replay, no rootfs writes, fine probe) measures 348.7 ms cdp p50 [343.5–351.7], 2.6× the 133.0 ms host warm pool (the same configuration's two golden generations measured 348.7 and 372.5; 4K-copy goldens measure 413–533 ms, 3.1–4.0×). On the PF-on 4K run (≈478 ms), the premium decomposes to ~1% virtualization and ~96% cold memory (330 of 345 ms; the rest is connection setup); the decomposition has not been re-measured on the newer configurations. Zero failures in every gated run, 202 measured requests per arm per run (the network-mode trio at 200). CPU is 650 core-ms per render, all-in. Four A/B questions are answered by measurement: on 4K pages minor is 14% slower than copy; on 2MB hugepages minor is 5–8% faster than copy, entirely in the restored browser's first CDP response (both same-golden); prefetch replay saves 285 ms (same-golden); and virtualization itself costs ~3 ms once memory is resident (cross-run, PF-on vs the host container). Minor with hugepages does not reserve the full 1024 MiB guest per clone: measured pool consumption is 553–611 MiB per concurrent clone at 1 GiB and 634–684 at 768 MiB, flat through N=32, against 133–146 on 4 K pages — the price of a 2 MB copy-on-write granule, not of the render. What remains open is the restore-vs-render CPU split and the corpus CPU figures. Every number above names the run that produced it.
