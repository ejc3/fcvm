Chromium in a microVM per request: a 618.6 ms median screenshot on Cloudflare’s corpus

Each request restores its own Firecracker microVM from a snapshot of a warm, unmodified Chromium, renders one page and discards the VM. The fastest run (4 guest vCPUs, UFFD copy mode, working-set prefetch on; run c4f-copy) returns a screenshot of a page from Cloudflare’s 14-URL corpus in a median of 618.6 ms, against 1,148 ms for Cloudflare’s Kitesurf (Rust compiled to WebAssembly on Workers) and 637 ms for its warm Chromium. The page’s HTML takes 591.3 ms, against 820 ms and 472 ms. The VM resumes 76.7 ms after launch in that run and 58.2 to 60.5 ms on the other 4 vCPU goldens; on one of those, polled every 5 ms, Chromium lists its page target at 267.0 ms (c4e-p5). It costs 2,344 ms of host CPU per screenshot against Kitesurf’s 380 ms, and 240 MiB per added clone on PSS against 57.8 MiB. Cloudflare’s figures are medians of five runs against the live sites; fcvm’s are 202 requests against a replay of the same pages, restore included (Same 14 URLs, different machines).

AWS c8g.metal-48xl (Neoverse-V2, 192 vCPUs), Ubuntu 24.04.5, kernel 7.0.0-1013-aws; guest 1024 MiB, Linux 6.18.50, Chromium 155.0.8059.79; Firecracker fork at 8819f112. Records and what they omit: Setup.

Where Cloudflare is ahead

  • HTML extraction, request median: 591.3 ms, against 472 ms for Cloudflare’s warm Chromium (Kitesurf 820 ms).
  • Host CPU per screenshot request, mean: 2,344 ms, against 380 ms for Kitesurf and 1,173 ms for Cloudflare’s warm Chromium.
  • Memory per added clone, screenshot (separate memory phase, 4 vCPUs, 2 to 48 clones held at once): 240 MiB on PSS (95% interval 190 to 290), 340 MiB (280 to 410) on the cgroup basis, against 57.8 MiB for Kitesurf and 271.0 MiB for Cloudflare’s Chromium, basis not stated.

What limits it now (run c4e, minor mode, 50 ms polling)

  • Guest restore work: before Chromium answers, fcvm’s agent in the guest retires the network connections the snapshot captured and reopens the clone: a median of 279.4 ms on the guest’s clock at 4 vCPUs (run c4e), 140.3 ms of it retiring sockets. It grows with the guest’s vCPU count (Guest restore work grows with vCPUs).
  • Navigate: Page.navigate to the load event is the largest part of a request, 527.8 ms of the 914.2 ms mean in run c4e, most of it on the slowest news sites.

Kitesurf rebuilds the browser; fcvm isolates it

Cloudflare’s post asks how to give every agent its own browser. Kitesurf builds a new engine from Workers components, each in its own V8 isolate: the Engine (the CDP session and fetches), PageScript (one isolate per navigation, for page script), PageRenderer (paints) and SandboxOutbound (the only path to the network), in Rust compiled to WebAssembly where it can, with parts of Blitz and Stylo. fcvm keeps unmodified Chromium and moves the isolation boundary out to a microVM per page.

Kitesurf does not yet support video playback, WebGL, a bot-challenge handshake with real TLS fingerprints, or a ten-minute authenticated session (Cloudflare’s post); it implements a subset of CDP. fcvm’s cost is the restore: at 4 guest vCPUs the VM resumes 59.0 ms after launch (Navigation is most of a request), and a restore with no render costs 338 to 494 ms of host CPU in the seven default 4 vCPU runs and 660 ms in copy mode (c4f-copy). Cloudflare publishes no spin-up time for a Kitesurf isolate.

Same 14 URLs, different machines

Cloudflare’s post reports “the medians of five Browser Run quick-action runs across a 14-URL corpus”. The corpus file, kitesurf.cloudflare.app/corpus.txt, is no longer served; the Wayback Machine holds identical copies from 2026-08-07 and 2026-08-14. We captured those 14 URLs and replay them to every clone.

The figures sit side by side, not in a controlled comparison. None of these differences is priced, so the orderings do not rank the systems:

  • Timer. Cloudflare’s post does not say what its timer covers or how a run combines its 14 URLs. Ours is the median of 202 requests, from launch to the answer.
  • Network. Cloudflare loads the live sites. Ours are replayed from the host, so no figure includes an internet round trip, and a request the capture missed gets an empty 404.
  • Browser state. Their Chromium is a warm pool, “Chrome reused between pages”. Each of our requests gets a fresh clone, as Kitesurf starts fresh, of a Chromium warmed on an unrelated page. Host Chromium without a VM measures a warm browser on our host.
  • CPU and memory. Cloudflare sums Kitesurf across its Worker components and measures Chrome’s memory as PSS. Ours is every process of the clone plus the memory server’s share (CPU and memory cost more than Kitesurf).
  • Hardware. Cloudflare does not state theirs; ours is in Setup.

Navigation is most of a request

  1. Golden, once. A VM boots Chromium, warms it on a local page, navigates to about:blank and is snapshotted. Every request restores this snapshot.
  2. Restore. A new Firecracker process restores a copy-on-write clone of the golden. Guest RAM is filled on first touch from the shared in-memory copy of the snapshot, and pages recorded from earlier clones start being mapped in after the handshake.
  3. Guest restore. fc-agent, fcvm’s agent in the guest, closes the network connections the snapshot captured and reopens the clone to new ones. Until it has, a connection to Chromium’s DevTools port ends in a reset.
  4. Wait for the target. The harness polls Chromium’s /json/list every 50 ms until a page target appears.
  5. Connect and navigate. WebSocket upgrade and Page.enable, then Page.navigate and a wait for Page.loadEventFired.
  6. Answer. Page.captureScreenshot, JPEG quality 80, or outerHTML for HTML extraction. The clock stops when the driver returns.
  7. Destroy, not timed. The clone and everything it wrote are discarded after the answer (median 63.7 ms in run c4e).

Navigate is the largest part of the mean, mostly on the slowest sites. The page’s own timing puts the load event at 254.2 ms from the start of navigation; the harness’s navigate stage, on the host’s clock, is 292.2 ms and holds the Page.navigate round trip of 31.1 ms (navigate_command_ms).

The forwarded DevTools port accepts at 51.0 ms, before the snapshot is loaded (58.6 ms) and the VM resumes (59.0 ms), so the harness polls while the restore runs; every poll until the page target appears ends in a reset (os-ECONNRESET). With 5 ms polls the target is listed at 267.0 ms, 207.2 ms after resume. fcvm marks the clone ready at 361.9 ms; the harness does not wait for it.

One memory image serves every clone

Two mechanisms set what a VM per request costs: minor mode shares one copy of the snapshot across clones, and replay maps the pages earlier clones faulted into each new clone before the guest faults on them.

A page a clone only reads is the same physical page in every clone; a page it writes is copied into that clone and discarded with it. In copy mode, the default for fcvm snapshot serve, each clone gets its own copy of every page it touches.

Prefetch off adds 240 ms

On 2 goldens at 4 vCPUs, each with a prefetch-on and a prefetch-off run in alternating order (cell.uffd_prefetch), turning prefetch off raised the request median by 238.0 to 242.0 ms and CPU per screenshot by 694 to 799 ms, and was slower on all 14 sites. With prefetch on the server mapped 579 to 603 MiB into each clone in 53 to 62 ms, and a clone took 2,034 to 2,292 demand faults, against 61,745 to 62,787 with it off.

CPU and memory cost more than Kitesurf

CPU per request

The cdp-fast, html-fast and noop-fast arms end each clone with one SIGKILL and read from /proc the CPU of every clone process (Firecracker, fcvm, pasta, the namespace holder), adding fcvm’s reaped helpers, exit-time freeing and the memory server’s share. Kernel threads, the driver and the replay server are not in it.

Memory with many clones at once

The memory phase holds N clones at once, each restored and rendered once (screenshot), then, interleaved, N warm Chromium containers on the host, each rendered once through the image’s render.py (a screenshot plus a DOM read, container_render). N is 2, 8, 16, 32 and 48, 14 times each, one per corpus page (schedule in run.json), at 4 vCPUs, minor mode, prefetch on. Two bases: the cgroup’s memory.current, which charges a page to the cgroup that touched it first, and PSS, which splits a shared page among its mappers. The memory server, which holds the one shared copy of the snapshot, is a median of 830 MiB on the cgroup basis and 10 MiB on PSS, once per host.

Intervals resample whole page blocks for both sides together, as the fits do. These are means; the per-instance column above is a median.

  • Resident (cgroup). Charges each page once, to the cgroup that first touched it. The memory server wrote the shared snapshot copy, so its cgroup holds all of it (841 MiB, mean), and a clone is charged for the pages it writes or allocates. Not in either side: pages of files first read before the cell, a once-per-host cost (the Chromium image’s binary and libraries for the containers; fcvm, Firecracker and pasta for the clones) that no record measures (fincore over those files at a steady sample would), and podman’s conmon and slirp4netns, which run outside each container’s cgroup. It includes page cache: 90 MiB (70 to 110) of a clone’s share at N = 48 is clone_file_kb (memory.stat file); the containers’ split is not recorded.
  • PSS. Splits a page among the processes that map it, so pages of the snapshot copy that no clone maps, and page cache nobody maps, count in nobody’s PSS; that is why the server is 10.7 MiB on PSS. On PSS the slope difference’s interval includes zero, so there is no crossing.
  • Host free memory. The fall in the host’s MemFree from each cell’s pre sample to its steady samples, plus the server, counts memory outside the cgroups too: 440 MiB per clone against 260 per container at N = 48. The fall in MemAvailable, which leaves out what the kernel counts as reclaimable, is 280 against 250, 21 MiB apart (12 to 31). Most of the clone’s extra is therefore page cache or reclaimable slab; the records do not say what it caches.

Throughput under load

An open-loop run offered 0.93, 1.40 and 1.87 screenshot requests per second on each of two restore paths at once, interleaved: the userfaultfd memory server (uffd, minor mode, prefetch on) and the snapshot file through the page cache (file), 4 vCPUs per clone. Each rate ran 5 scored 60 s bursts after a 15 s ramp. A rate passes when every burst offered its rate within 2%, completed at least 95% of it inside the window with a backlog of at most 128, kept the 95th-percentile launch lag under 50 ms with every request succeeding, and a host Chromium drift check moved less than 15%. The highest rate that passed on both paths was 1.40 per second per path.

Four vCPUs beat two; eight add little

The vCPU count is fixed in the golden: 2 runs on 2 goldens at 2 vCPUs, 7 on 5 at 4, and 2 on 2 at 8, interleaved over the day on 4 host boots, so the spread within a rung is run-to-run variance.

Every 4 vCPU run is faster than every 2 vCPU run (683.4 to 715.5 ms against 777.0 to 805.3 ms), and 8 vCPUs (671.6 to 704.6 ms) overlaps 4. Each step shortens navigate (411.3 to 413.4, then 288.4 to 300.8, then 258.2 to 269.7 ms) and lengthens the wait for the target by about one 50 ms poll (203.8 to 204.0, then 253.6 to 254.7, then 303.8 to 304.5 ms), as fc-agent’s restore work grows (Guest restore work grows with vCPUs).

Limits

What this campaign does not measure, and why:

  • Memory and throughput at 2 and 8 vCPUs. Not run; each takes about three hours of host time per vCPU count.
  • WebKit. Its golden failed on a --version flag WebKitWebDriver does not have; the harness is fixed (873d12c3, REVIEW.md harness bug 19) and the run was not repeated.
  • 2 MiB pages on the corpus. Not run.
  • A third run at 2 and 8 vCPUs. Those rungs have two runs each.
  • Live origins. Every request is served by the replay on the host, which keeps the origins’ own variation out of every number.
  • Other network modes. Every run uses rootless networking (pasta). The replay is reached at pasta’s gateway address, 10.0.2.2, which bridged and routed clones do not have; a bridged run of an earlier synthetic page failed the zero-failure gate at 1 failure in 205 requests (#820).

Method and gates

  • Sample gate. A run publishes only with at least 200 measured requests per render arm and zero failures over every attempt, warmups included. Zero failures in every published cell: each of the 15 corpus runs has 0 failures in 230 attempts per arm, an exact (Clopper-Pearson) 95% interval of 0 to 1.59%.
  • Quiet host. A run starts only below a 1-minute load of 2.0, and the campaign waits for 1.5 before measuring; each request records the load (loadavg1).
  • Runtime seal. The harness hashes itself, fcvm and fc-agent into a bundle and does not measure a golden made under a different bundle.
  • Drift gate. The 95% confidence interval of an interleaved no-render arm’s shift between the run’s halves must lie within 10 ms either way. Every run passed.
  • DNS verification. Each run checks three times that the replay server answered every corpus host with 10.0.2.2, and samples every 10 s that it owns port 53. Every run’s dns-evidence.json reads clean.
  • Diagnostics. Before measuring, each golden renders every URL three times on traced clones, and the campaign stops before measuring if a request reaches any address but the replay, a page takes over 15 s, or a name fails to resolve (diag/summary.json).
  • Replay fidelity. 12 of the 14 sites render the same from the replay as live (DOM similarity at least 0.90, under 10% of pixels changed); the other two differ only in ad slots and consent overlays. The result is in the message of commit f7d54690.
  • Lints. bench/chromium/test_reqbench.py checks that every figure in the serial-run tables and tiles equals, at its printed precision, a value some DNS-verified run’s record holds (not the cited run’s own field), and rejects withdrawn figures; bench/chromium/test_report_page.py checks Cloudflare’s rows against its published table.

To reproduce a corpus run (golden, verification, DNS diagnostics, measured run) from a clean checkout:

make bench-chromium-corpus ARMS=cdp,cdp-fast,html-fast,noop,noop-fast CPU=4

Each vCPU count and page size needs its own golden. The targets and knobs for every phase, including the memory phase (make bench-chromium-corpus-extra) and the throughput run (MEASURE=scale), are in bench/chromium/AGENTS.md.

Firecracker builds

fcvm drives a fork, ejc3/firecracker, at the commit rootfs-config.toml pins; every serial run records the binary it restored on, its sha256 and the pinned commit, which the harness ties to the binary (cell.firecracker.commit and commit_matches_binary in analysis.json).

2026-10-22 runs

Branch agent/uffd-minor-v1.17.0-discard-dirty at 8819f112, committed 2026-10-08: upstream’s release v1.17.0 (95f868c8e3, 2026-09-04) plus 19 commits, built as firecracker-default-0834213edfce.bin, sha256 955e505483cb… in every run (cell.firecracker.sha256).

  • Minor-fault memory backend. Guest RAM maps the memory server’s sealed memfd MAP_PRIVATE and takes minor faults on it. Every minor-mode run here depends on it.
  • Discarded memory in snapshots. Guest pages a discard emptied (balloon, free page reporting) are written to the next snapshot as zeros, and all-zero pages stay holes in a full snapshot written to an empty file.

Restored guests keep their monotonic clock: on these plain-EL1 guests KVM recomputes the counter offset at restore (the March 2023 arm64 counter-offset series), so the nested-virtualization timer storm (#630) does not apply.
