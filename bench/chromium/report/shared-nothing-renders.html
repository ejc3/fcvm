Harness and records

One microVM per page: Chromium on Firecracker snapshots

In August Cloudflare introduced Kitesurf, a browser for agents that runs on Workers, one V8 isolate per navigation, and uses native Rust compiled directly to WebAssembly where possible. Their starting point is that Chromium is too heavy: it uses “so much memory and compute that providing every agent with its own instance is prohibitively expensive”. This page looks at the other answer: keep unmodified Chromium and give each request its own microVM, restored from a snapshot in which Chromium is already booted and warm, with the memory server recording which pages clones touch and mapping them into the next one. On Cloudflare’s 14-URL corpus it measures how long a request takes, how much host CPU it uses, how much memory clones held at once take, and which request rates one host kept up with.

Two answers to one question

Cloudflare’s post asks how to give every agent its own browser. Kitesurf answers with a new engine built as several Workers components, each in its own V8 isolate: the Engine, which holds the CDP session and fetches the page’s document and scripts; PageScript, one isolate per navigation, which runs the page’s script; PageRenderer, which paints; and SandboxOutbound, the only path to the network. Where it can, it uses native Rust compiled to WebAssembly, with parts of Blitz and Stylo for HTML and CSS. fcvm keeps the engine and moves the isolation boundary out to a microVM, so that each page gets its own kernel under an unmodified Chromium.

The two designs pay for isolation in different places. Kitesurf rebuilds the engine as Workers components, and Cloudflare’s post lists what it cannot do yet: play video, render WebGL, negotiate a bot-challenge handshake with real TLS fingerprints, or start a ten-minute authenticated session that requires persistent state. It implements a subset of CDP. fcvm keeps the whole engine and restores a VM for each request instead of booting one. At 4 guest vCPUs the restored VM resumes a median of 59.0 ms after launch, and Chromium’s DevTools lists a page target 304.6 ms after launch when polled every 50 ms (What one request does). A restore with no render costs a mean of 338 to 494 ms of host CPU per request across the 4 vCPU runs. For scale only, Cloudflare’s later benchmark leaves out the launch of a fresh Chrome, a median of 215 ms across its pages, on hardware it does not state. Cloudflare publishes no spin-up time for a Kitesurf isolate.

The same corpus

Cloudflare’s post reports “the medians of five Browser Run quick-action runs across a 14-URL corpus”, Kitesurf against Chromium in a warm pool. The corpus file, kitesurf.cloudflare.app/corpus.txt, is no longer served; the Wayback Machine holds identical copies from 2026-08-07 and 2026-08-14. We captured those 14 URLs and replayed them to a new microVM per request.

These figures sit side by side; they are not a controlled comparison. The setups differ:

  • Statistic and timer. Cloudflare’s figures are “the medians of five Browser Run quick-action runs”; the post does not say how each run combines its 14 URLs or what its timer covers. Ours is the median of 202 requests per run, from launch to the answer returned. Our per-run means at 4 vCPUs are 913.3 to 952.1 ms.
  • Uncaptured requests. The replay answers an uncaptured GET, HEAD or POST with an empty 404. A live load would fetch those resources and whatever they trigger.
  • Network. Cloudflare’s corpus names live public URLs, and the post does not state how benchmark traffic was controlled. Our corpus is replayed from the same host, so our numbers contain no internet round trips.
  • Browser state. Their Chromium column is a warm pool; Cloudflare’s later benchmark page describes that arm as “Chrome reused between pages”. Each of our requests gets its own clone and discards it afterwards, so no browser state carries from one request to the next, as in their Kitesurf column. Unlike Kitesurf, each clone starts from a Chromium that was booted and warmed on an unrelated local page before the snapshot: neither a cold engine nor a browser that has seen the measured pages. Host Chromium without a VM measures a warm Chromium on our host, in-process driver and container CPU, as a control.
  • CPU and memory basis. Cloudflare’s later benchmark page measures Browser Run’s CPU at container level and the Chrome arms’ memory as PSS across Chrome’s processes, and sums Kitesurf’s across its Worker components. Our CPU is every process of the clone plus the memory server’s share, and our memory is the cgroup and PSS of every process of the clone (CPU, memory and throughput).
  • Feature scope. Cloudflare’s post says Kitesurf cannot yet play video, render WebGL, negotiate a bot-challenge handshake with real TLS fingerprints, or start a ten-minute authenticated session that requires persistent state. We run unmodified Chromium.
  • Hardware. Cloudflare does not state theirs. Ours is in Setup.

As numbers, at 4 vCPUs our screenshot medians (683.4 to 715.5 ms) are below Kitesurf’s 1,148 ms and above their warm Chromium’s 637 ms, and our HTML medians (615.3 to 658.4 ms) are below Kitesurf’s 820 ms and above their warm Chromium’s 472 ms. Our CPU per request (2,165 to 2,398 ms for a screenshot, 2,059 to 2,267 ms for HTML extraction) is above both of their engines’ figures. None of the differences listed above is priced, so the orderings do not rank the systems.

What one request does

  1. Golden, once. A VM boots Chromium, warms it on a local page, navigates to about:blank and is snapshotted. Every request restores this snapshot.
  2. Restore. A new Firecracker process restores a copy-on-write clone of the golden. Guest RAM is filled on first touch from the shared in-memory copy of the snapshot, and pages recorded from earlier clones start being mapped in after the handshake.
  3. Guest restore. fc-agent, fcvm’s agent in the guest, closes the network connections the snapshot captured and reopens the clone to new ones. Until it has, a connection to Chromium’s DevTools port ends in a reset.
  4. Wait for the target. The harness polls Chromium’s /json/list every 50 ms until a page target appears.
  5. Connect and navigate. WebSocket upgrade and Page.enable, then Page.navigate and a wait for Page.loadEventFired.
  6. Answer. Page.captureScreenshot, JPEG quality 80, or outerHTML for HTML extraction. The clock stops when the driver returns.
  7. Destroy, not timed. The clone and everything it wrote are discarded after the answer (median 63.7 ms in run c4e).

Navigate is the largest part of the mean, and the slowest sites make most of it. Inside it, the page’s own Navigation Timing marks put the document received at a median of 14.5 ms, the DOM interactive at 111.9 ms and the load event at 254.2 ms from the start of the navigation, against 292.2 ms for the harness’s navigate stage; the stage also holds the Page.navigate command’s own round trip, a median of 31.1 ms (navigate_command_ms).

Launching the VM to the first accepted connection on the forwarded DevTools port takes a median of 51.0 ms. That port is pasta’s host-side listener, which accepts before the snapshot is loaded, so the harness starts polling for the page target while the restore is still running. fcvm’s log marks the snapshot loaded at 58.6 ms and the VM resumed at 59.0 ms. Every poll from the first one until the page target appears ends in a reset (os-ECONNRESET; every miss in these runs is one). The records do not say which side sends it; some resets come before the VM has resumed, so not all of them can come from the guest. With polls every 5 ms, the last reset poll comes at a median of 260.0 ms and the page target is listed at 267.0 ms, a median of 207.2 ms after that request’s resume. fcvm marks the clone ready at 361.9 ms, once fc-agent’s acknowledgement has arrived and the port forward is verified; the harness does not wait for it.

fc-agent times its own restore work, on the guest’s clock, and sends the phases to the host with its acknowledgement. Its time grows with the guest’s vCPU count, and so does the wait for the target, timed on the host. The two have different start and end points, so neither is the other; the records show them growing together:

One snapshot, many clones

Two mechanisms shape what a VM per request costs. The first is memory sharing: in minor mode the pages a clone only reads are a read-only view of one copy of the snapshot. The second is profiling and replay: the memory server records which pages clones fault and starts mapping that set into each new clone after the handshake, before it resumes.

A page one clone reads costs no memory in the others: every clone maps the same physical page. A page a clone writes is copied into that clone on its first write and discarded with it. The snapshot never changes. In copy mode, the default for fcvm snapshot serve, each clone instead gets its own copy of every page it touches.

Each pair ran on one golden at 4 vCPUs, one run with prefetch on and one with it off, in alternating order; the memory server reported its setting in each run (cell.uffd_prefetch). CPU, memory and throughput

CPU per request

The cdp-fast, html-fast and noop-fast arms end each clone with one SIGKILL and read, from /proc, the CPU time every process of the clone used: Firecracker, whose threads run the guest’s vCPUs and the device emulation; fcvm; pasta; the namespace holder. To that the harness adds what fcvm’s short-lived helpers used (fcvm’s reaped-children counters), the CPU each process spent freeing its memory as it exited, and the memory server’s CPU over the request. Kernel threads are not in it: the deletion of the clone’s disk, network softirq work and the like are charged to no process of the clone. Neither is the harness’s own driver, or the replay server that stands in for the sites.

Memory with many clones at once

The memory phase holds N fcvm clones at once, each restored and rendered once (a corpus page, screenshot), and samples them; then, interleaved with them, N warm Chromium containers on the host, each having rendered one page through the image’s own driver, render.py, which takes a JPEG screenshot and then reads the DOM (container_render in the record), one step more than a clone’s render. N ran 2, 8, 16, 32, 48, 14 times each, at 4 vCPUs per clone, with prefetch on and minor mode. Each repetition renders one corpus page on all N instances, and the 14 repetitions are the 14 pages, so the ranges and intervals below are across pages, not repeats of one mix (schedule in run.json). Two bases: the cgroup’s memory.current, which charges each page to the cgroup that first touched it, and PSS, which splits a shared page among the processes that map it. A clone’s cgroup holds fcvm, Firecracker, the namespace holder and pasta; a container’s is podman’s. The memory server, with the one shared copy of the snapshot, sits in a cgroup of its own: a median of 830 MiB on the cgroup basis and 10 MiB on PSS, once per host.

Throughput under load

An open-loop run offers requests at a fixed rate without waiting for earlier ones, and checks that the host keeps up. It ran 0.93, 1.40, 1.87 requests per second (56, 84, 112 in each 60 s scoring window, whole cycles of the 14 pages) on each of two restore paths at once: clones restored through the userfaultfd memory server (uffd, minor mode, prefetch on) and clones restored from the snapshot file through the page cache (file), interleaved request by request, with screenshot requests on the 14 corpus pages and 4 guest vCPUs per clone; the scale record names neither the page size nor a poll interval. Each rate had 5 scored bursts of 60 s after a 15 s ramp, in seeded order, after 1 warmup burst; a Chromium on the host rendered one page throughout as a drift check. A rate passes when every burst at it offered its rate within 2%, completed requests inside the scoring window at 95% of that rate or more, ended with a backlog of at most 128 requests, kept the 95th percentile of its launch lag under 50 ms and had every request succeed, and the host Chromium’s median moved less than 15%. The highest rate that passed for both, with every lower rate passing too, was 1.40 requests per second per restore path.

Host Chromium without a VM

The control runs Chromium from a build of the same container image directly on the host, with no VM: one warm browser whose page target is navigated to each request’s URL by the same CDP driver as the clones, loaded into the harness’s own process (driver_process in-process), so no interpreter start-up is in any time. Chromium resolves every host to 127.0.0.1, where the replay listens on the host, as the clones resolve theirs to the replay through their gateway. Each arm ran 202 measured requests after 28 warmup over the 14 URLs, once without a CPU limit and once each limited to 2, 4 and 8 CPUs by the container’s CPU quota. Request time is from the driver’s start until it returns; a clone’s also holds launching and restoring its VM, which this browser never does. Container CPU is everything the container’s cgroup used from the first measured request’s start to the last one’s end, divided by the number of requests, so it includes the browser’s work between requests; the driver runs outside the container and is not in it.

Limits

What this campaign does not measure, and why:

  • Memory and throughput at 2 and 8 vCPUs. Both ran at 4 guest vCPUs only. The memory phase and the throughput run take about three hours of host time per vCPU count, and this campaign spent its host time on the comparisons above.
  • WebKit. The WebKit run did not start: its golden asked WebKitWebDriver for a --version it does not have and refused itself. The harness now reads the version from the webkit2gtk-driver package (873d12c3, REVIEW.md harness bug 19), and the run, about 40 minutes, was not repeated within this campaign’s host time.
  • 2 MiB pages on the corpus. The planned minor, copy, minor A/B/A on a 2 MiB golden, about 90 minutes, was dropped for host time; the 2 MiB comparison remains the synthetic page’s under Earlier runs.
  • A third run at 2 and 8 vCPUs. Those rungs have two runs each, so their ranges are over two runs. A third run at each, and a third prefetch pair, about two and a half hours in all, were dropped to keep the campaign near one day of host time.
  • Live origins. Every request is served by the replay on the host, so no figure here includes an internet round trip, and the requests the capture did not hold get an empty 404 instead of a body (The same corpus). Measuring against the live sites would put the origins’ own variation into every number; the replay exists to keep it out.
  • Other network modes. Every run uses rootless networking (pasta). The corpus replay reaches the host at the gateway address pasta gives each clone, 10.0.2.2, which bridged and routed clones do not have, so running them on the corpus needs a different replay path first. A bridged run of the earlier synthetic page was refused by the zero-failure gate at 1 failure in 205 requests (#820, closed 2026-08-15).

Method and gates

  • Sample gate. A run publishes only with at least 200 measured non-warmup requests in each render arm and zero failures over every attempt, warmups included; otherwise the analyzer exits 5. Zero failures in every published cell: each of the 15 corpus runs on this page has 0 failures in 230 attempts in every arm (202 measured plus 28 warmups), an exact 95% (Clopper-Pearson) interval of 0 to 1.59% per arm and run.
  • Quiet host. A run refuses to start above a 1-minute load of 2.0. The campaign waits for the load to fall below 1.5 after the diagnostics, and again after the last DNS check, just before measuring. During a run the load is not gated; each request records it (loadavg1).
  • Runtime seal. The harness hashes itself, fcvm and fc-agent into a bundle and refuses to measure a golden made under a different bundle.
  • Drift gate. The no-render arm runs interleaved through every run. The analyzer compares its first and second halves and marks the run unpublishable unless the 95% confidence interval of the shift lies within 10 ms either way. Every run on this page passed it.
  • DNS verification. Each corpus run resolves every corpus host from a clone three times (before the settle wait, just before measuring and just after), and each check passes only if the replay server’s own log shows an A answer of 10.0.2.2 for all 10 corpus hosts in the rows it added during that check. A sampler records every 10 s of the measured run that the replay server owns port 53 and dnsmasq is inactive. The verdict is written to dns-evidence.json; every run on this page reads clean.
  • Diagnostics. Before measuring, each golden renders every corpus URL three times on traced clones with prefetch off (uffd_prefetch in diag/summary.json), and the campaign refuses to measure if any request reaches an address other than the replay server, any page fails to load within 15 s, or any name fails to resolve (diag/summary.json).
  • Replay fidelity. 12 of the 14 sites pass the replay equivalence check: DOM similarity at least 0.90 and under 10% of pixels changed, where a pixel counts as changed when the grayscale value of its per-channel difference is 16/255 or more. The two that fail are news sites whose pixel differences are confined to ad slots and consent overlays, whose third-party requests were not captured. The check’s report is not committed; its result is in the message of commit f7d54690.
  • Lints. bench/chromium/test_reqbench.py checks the figures in the page’s serial-run tables and the verdict tiles’ medians against the committed records: each must equal, at its printed precision, a median, interval bound or mean that some DNS-verified run’s analysis.json or restore-ack.jsonl holds (a pooled set, not the cited run’s own field), rejects withdrawn figures, and keeps Cloudflare’s medians out of sentences that quote our within-run intervals. bench/chromium/test_report_page.py checks Cloudflare’s rows against the published table and the page’s structure.

To reproduce a corpus run (golden, verification, DNS diagnostics, measured run) from a clean checkout:

make bench-chromium-corpus ARMS=cdp,cdp-fast,html-fast,noop,noop-fast CPU=4

The guest vCPU count and the page size are part of the golden, so each rung of a ladder needs its own golden. The phase-by-phase targets and knobs, including the memory and host-control phases (make bench-chromium-corpus-extra) and the throughput run (MEASURE=scale), are in bench/chromium/AGENTS.md.

Firecracker builds

fcvm drives a fork, ejc3/firecracker. rootfs-config.toml at each run’s fcvm source revision pins a branch and a commit, and setup builds that commit. Every serial run in the campaign records the binary it restored on, its sha256, and the pinned commit, which the harness ties to the binary by the file name setup gives a build of that commit (cell.firecracker in analysis.json).

2026-10-22 runs

Branch agent/uffd-minor-v1.17.0-discard-dirty at 8819f112, committed 2026-10-08: upstream’s release v1.17.0 (95f868c8e3, 2026-09-04) plus 19 commits, built as firecracker-default-0834213edfce.bin, sha256 955e505483cb… in every run (cell.firecracker.sha256).

  • Minor-fault memory backend. During the userfaultfd handshake the fcvm memory server passes a sealed memfd holding the snapshot’s memory. Firecracker maps guest RAM MAP_PRIVATE over it and registers it for minor faults, with 2 MiB pages when the snapshot has them. Every minor-mode run here depends on it.
  • Discarded memory in snapshots. Guest pages a discard emptied (balloon, free page reporting) are written to the next snapshot as zeros, and all-zero pages stay holes in a full snapshot written to an empty file.

Earlier runs

The 2026-09-02 and 2026-08-30 corpus runs used branch agent/uffd-minor (upstream main as of 2026-08-07 plus the minor-fault backend and a raised vsock connection limit), and the synthetic-page runs branch bump-vsock-max-connections. Their records do not store the commit; the 2026-09-02 runs’ hostinfo.json stores the binary’s sha256.

Restored guests need their monotonic clock to continue from the snapshot instant, or every armed timer fires at once. On these plain-EL1 guests the host kernel handles it: since the March 2023 arm64 KVM counter-offset series, KVM recomputes the VM-wide counter offset when a restore replays the saved counter registers. The timer storm fcvm fixed for nested virtualization (#630) needs a virtual-EL2 guest and does not apply here.
