Harness and records

Chromium in a microVM per request: a 476.4 ms median screenshot on Cloudflare’s corpus

Each request restores its own Firecracker microVM from a snapshot of a warm, unmodified Chromium, renders one page and discards the VM. At 8 vCPUs, UFFD minor mode and working-set prefetch on, a screenshot of a page from Cloudflare’s 14-URL corpus takes a median of 476.4 ms (the median of three runs, each on its own snapshot: 473.3 to 480.0 ms), and the page’s HTML 411.4 ms (408.0 to 416.5). The VM resumes 62.1 ms after launch and Chromium lists its page target at 92.2 ms. A screenshot costs 2,659 ms of host CPU, and each added clone holds 250 MiB on PSS (CPU and memory). Cloudflare publishes 1,148 ms for Kitesurf (Rust compiled to WebAssembly on Workers) and 637 ms for its warm Chromium, measured on its own platform against the live sites (Same 14 URLs, different machines).

AWS c8g.metal-48xl (Neoverse-V2, 192 vCPUs), Ubuntu 24.04.5 LTS, kernel 7.0.0-1013-aws; guest 1024 MiB, Linux 6.18.50, Chromium 156.0.8078.79 built on Debian GNU/Linux 12 (bookworm); Firecracker fork at 3057dcb7. Every figure is from one campaign, on 3 hosts of that type at one fcvm commit: Setup.

Kitesurf rebuilds the browser; fcvm isolates it

Cloudflare’s post asks how to give every agent its own browser. Kitesurf builds a new engine from Workers components, each in its own V8 isolate: the Engine (the CDP session and fetches), PageScript (one isolate per navigation, for page script), PageRenderer (paints) and SandboxOutbound (the only path to the network), in Rust compiled to WebAssembly where it can, with parts of Blitz and Stylo. fcvm keeps unmodified Chromium and moves the isolation boundary out to a microVM per page.

Cloudflare’s post says Kitesurf doesn’t support video playback, WebGL, a bot-challenge handshake with real TLS fingerprints, or a ten-minute authenticated session, and that it implements a subset of CDP. fcvm’s cost is the restore: at 4 guest vCPUs the VM resumes 61.2 ms after launch (Navigation is most of a request), and a restore with no render costs 331 ms of host CPU (327 to 341 over the three runs). Cloudflare publishes no spin-up time for a Kitesurf isolate.

Same 14 URLs, different machines

Cloudflare’s post reports “the medians of five Browser Run quick-action runs across a 14-URL corpus”. The corpus file, kitesurf.cloudflare.app/corpus.txt, is no longer served; the Wayback Machine holds identical copies from 2026-08-07 and 2026-08-14. We captured those 14 URLs and replay them to every clone.

The two sets of figures come from setups that differ in these ways, so the bars sit side by side as a third-party comparison:

  • Timer. Cloudflare’s post doesn’t say what its timer covers or how a run combines its 14 URLs. Ours is the median of 202 requests, from launch to the answer.
  • Network. Cloudflare loads the live sites. Ours are replayed from the host, so no figure includes an internet round trip (Method).
  • Browser state. Their Chromium is a warm pool, “Chrome reused between pages”. Each of our requests gets a fresh clone, as Kitesurf starts fresh, of a Chromium warmed on an unrelated page. Host Chromium without a VM measures a warm browser on our host.
  • CPU and memory. Cloudflare sums Kitesurf across its Worker components and measures Chrome’s memory as PSS. Ours is every process of the clone plus the memory server’s share (CPU and memory).
  • Hardware. Cloudflare doesn’t state theirs; ours is in Setup.

Navigation is most of a request

  1. Golden, once. A VM boots Chromium, warms it on a local page, navigates to about:blank and is snapshotted. Every request restores this snapshot.
  2. Restore. A new Firecracker process restores a copy-on-write clone of the golden. Guest RAM is filled on first touch from the shared in-memory copy of the snapshot, and pages recorded from earlier clones start being mapped in after the handshake.
  3. Guest restore. fc-agent, fcvm’s agent in the guest, closes the network connections the snapshot captured and reopens the clone to new ones. Until it has, a connection to Chromium’s DevTools port ends in a reset.
  4. Wait for the target. The harness polls Chromium’s /json/list every 5 ms until a page target appears.
  5. Connect and navigate. WebSocket upgrade and Page.enable, then Page.navigate and a wait for Page.loadEventFired.
  6. Answer. Page.captureScreenshot, JPEG quality 80, or outerHTML for HTML extraction. The clock stops when the driver returns.
  7. Destroy, not timed. The clone and everything it wrote are discarded after the answer (mean 72.9 ms in run r3-c4).

Guest restore work

Before Chromium answers, fc-agent retires the network connections the snapshot captured and reopens the clone to new ones. The barrier before the sockets are retired waits an expedited RCU grace period, and the network gate is verified and removed over netlink without starting a process. Across the Chromium runs at 2, 4 and 8 vCPUs that work takes a median of 19.8, 13.2 and 14.1 ms on the guest’s clock:

One memory image serves every clone

Two mechanisms set what a VM per request costs: minor mode shares one copy of the snapshot across clones, and replay maps the pages earlier clones faulted into each new clone before the guest faults on them.

Kernel threads, the driver and the replay server are not in it.

Throughput under load

An open-loop run offered 1.4, 2.8 and 4.2 screenshot requests per second on each of two restore paths at once, interleaved: the userfaultfd memory server (uffd, minor mode, prefetch on) and the snapshot file through the page cache (file). Each rate ran 5 scored 60 s bursts after a 15 s ramp, at 2, 4 and 8 guest vCPUs. A rate passes when every burst offered its rate within 2%, completed at least 95% of it inside the window with a backlog of at most 128, kept the 95th-percentile launch lag under 50 ms with every request succeeding, and a host Chromium drift check moved less than 15%.

Limits

  • Cloudflare’s figures come from a setup we cannot run. Method and gates

  • Replay. The corpus is served to every clone from a capture of the live sites, by a replay server on the host whose DNS answers every name with its own address. This keeps the origins’ own variation, and the internet, out of every request: each figure measures fcvm and Chromium against the same bytes. An uncaptured GET, HEAD or POST gets an empty 404, and a CORS preflight gets 204 (bench/chromium/corpus_serve.py). Rootless clones reach the replay at pasta’s gateway 10.0.2.2, bridged clones at 192.168.53.2 and routed clones at fd53::2, an address the campaign assigns to a host device for each run.
  • Sample gate. A run publishes only with at least 200 measured requests per render arm and zero failures over every attempt, warmups included. Zero failures in every published cell: each of the 33 serial corpus runs has 0 failures in 230 attempts per arm (rootless), an exact (Clopper-Pearson) 95% interval of 0 to 1.59%, or 0 failures in 430 attempts per arm (bridged and routed, which run 402 measured requests per arm), an interval of 0 to 0.85%.
  • Quiet host. A run starts only at or below a 1-minute load of 2.0; the highest load at a run’s start in this campaign was 1.42 (quiet_guard_loadavg1 in each meta line), and each request records the load (loadavg1).
  • Runtime seal. The harness hashes itself, fcvm and fc-agent into a bundle and doesn’t measure a golden made under a different bundle.
  • Drift gate. The 95% confidence interval of an interleaved no-render arm’s shift between the run’s halves must lie within 10 ms either way. Every run passed.
  • DNS verification. Each run checks three times, inside a restored clone, that every corpus host resolves to the replay and that the replay server answered those queries, and samples every 10 s which process owns the replay’s DNS socket. Every run’s dns-evidence.json reads clean.
  • Diagnostics. Before measuring, each golden renders every URL three times, Chromium on traced clones, and the campaign stops before measuring if a traced request reaches any address but the replay, a page takes over 15 s, or a name fails to resolve; WebKit renders carry no trace, so its runs check that every render succeeds within the time (diag/summary.json).
  • Lints. bench/chromium/test_report_one_campaign.py checks that every record the page cites belongs to this campaign and that the records agree on the commit, the instance type, the Firecracker binary and, per engine, the image, the browser and the runtime bundle; test_report_page.py checks Cloudflare’s rows against its published table.

To reproduce a serial run (golden, verification, DNS diagnostics, measured run) from a clean checkout at the campaign’s commit:

make bench-chromium-corpus ARMS=cdp,cdp-fast,html-fast,noop,noop-fast CPU=4

Each vCPU count, page size and network mode needs its own golden (CPU=, HUGEPAGES=1, NETMODE=). The targets and knobs for every phase, including the memory phase (make bench-chromium-corpus-extra) and the throughput run (MEASURE=scale), are in bench/chromium/AGENTS.md; the campaign’s run order is results/campaign-40657613-plan.tsv.
