One microVM per page: Chromium on Firecracker snapshots

fcvm answers each screenshot request with a new Firecracker microVM, restored from a snapshot of a Chromium that is already booted and warm. The VM renders one page, returns a JPEG and is destroyed. Requests share nothing but the read-only snapshot. This page reports what that costs on Cloudflare’s 14-URL Kitesurf corpus, and which parts of the design make it fast.

Against Cloudflare’s numbers

Cloudflare’s Kitesurf post measures per-request browser isolation on the same 14 URLs: Kitesurf, a rebuilt browser engine isolated per request, against a pool of warm Chromium instances. We ran unmodified Chromium in a new microVM per request.

These are two sets of medians side by side, not a controlled comparison. The setups differ in ways that push in both directions:

  • Network. Cloudflare loaded the live pages over the internet. Our corpus is replayed from the same host, so our numbers contain no internet round trips. This favors us.
  • Unanswered requests. The replay leaves ad and consent request chains unanswered, and Chromium waits them out on the news sites. A live load would have answered them. This works against us.
  • Browser state. Their Chromium column reuses a warm browser between requests. Every one of our requests restores a new VM from the snapshot and discards it afterwards, which is closer to their Kitesurf column.
  • Hardware. Cloudflare does not state theirs. Ours is in Setup.

With those caveats, our median is lower than their isolated Kitesurf median at every vCPU count we ran, and lower than their warm Chromium median at 4 and 8 vCPUs but not at 2.

What one request does

  1. Snapshot, once. A golden VM boots Chromium, warms it on a local warm-up page, navigates to about:blank and is snapshotted: memory, disk and device state.
  2. Restore. A new Firecracker process restores a copy-on-write clone. Guest RAM is served on first touch from the snapshot file; pages earlier clones used are prefetched.
  3. Wait for the target. The harness polls Chromium’s /json/list every 50 ms until a page target appears.
  4. Connect and navigate. WebSocket upgrade, Page.enable, then navigate to the URL. Fetch, script, layout and paint happen here.
  5. Screenshot. Page.captureScreenshot, JPEG quality 80.
  6. Destroy. The clone and everything it wrote are discarded.

Restoring the VM is not the expensive part. The median restore takes 44.7 ms; rendering the page, navigation plus screenshot, dominates.

The wait for the target is mostly the harness’s own sleep. The stage is a poll with 50 ms sleeps, so it moves in 50 ms steps: the median request at 4 vCPUs polled 4 times, and 3.2 ms of the stage is not sleep. When Chromium’s target actually became ready inside the last step is not measured, so replacing the poll with a readiness notification would save at most one 50 ms interval per request. That change has not been measured.

Guest vCPU count

The vCPU count is baked into the snapshot, so each rung of this ladder is its own golden. The three rungs ran back to back on one host with one build.

Going from 2 to 4 vCPUs is the step that matters: 549.4 ms is 28.7% below 770.3, and all 14 sites are faster at 4 than at 2. From 4 to 8 the medians do not separate. Each sits inside the other’s interval, and 8 vCPUs is slower than 4 on 11 of the 14 sites.

The 4-to-8 difference is not in the rendering. Navigate falls from 301.0 to 267.2 ms and screenshot from 67.1 to 64.1 ms, while the wait for the target rises from 153.1 to 204.6 ms: one extra 50 ms poll (median attempts 4, then 5). So 4 vCPUs is the latency operating point. More vCPUs per render also means fewer renders per host, and no run here measures density.

No configuration was measured twice under the same conditions. The two 2 vCPU runs, on different goldens, fcvm builds and host boots, read 770.3 and 712.6 ms, 57.7 ms apart; that is the only view of run-to-run spread here. The host’s 1-minute load peaked at 2.62, 18.3 and 16.97 during the 2, 4 and 8 vCPU runs, while the no-render baseline stayed at 44.9, 45.1 and 45.8 ms.

Correction

An earlier corpus series, from 2026-08-16, is withdrawn. Before fcvm 90733b854e, pasta redirected the guest’s DNS to the host’s resolver, so those runs resolved third-party hosts on the live internet and waited on them. Every corpus run on this page has a verified resolver: each run’s DNS queries were answered only by the replay server. The withdrawn records and their evidence are in REVIEW.md.

What makes a restore fast

Synthetic page

This section uses medium.html, a small deterministic page (1.4 KB of HTML, one stylesheet, 806 B of script, four images) served with Cache-Control: no-store, on the Graviton3 fixture host. It exists to compare configurations. Absolute numbers vary by about 25% between goldens, so only pairs measured on the same golden are compared, and none of these numbers is comparable to the corpus results above.

A restored clone faults in almost the same pages every time: 65 to 69% of the faulted set is shared between restores, and 59% of faults fall in runs of 4 or more consecutive pages. The memory server records that set and populates it at restore, off the request path. On the same golden that cuts the median by 284.7 ms (37%), and the restore stage stays at 59.3 ms.

In copy mode every faulting page is copied into the clone. In minor mode the page already sits in a shared in-memory file and is only mapped, so clean pages are shared between clones. With 2 MB hugepages and minor mode no userspace faults happen at all. A file-backed restore uses the kernel page cache and has no userspace fault path.

Not measured

  • CPU and memory per request on the corpus. Cloudflare publishes both; we have no whole-system CPU figure and no memory figure on a reconciled basis.
  • HTML extraction, Cloudflare’s second operation. No run performs it.
  • Density. How many concurrent renders a host sustains, and at what latency.
  • Run-to-run variance. No configuration was measured twice under the same conditions. Five independent runs per configuration would put error bars on the medians.
  • Other network modes. Only rootless (pasta) is published. A bridged-network run was refused by the zero-failure gate at 1 failure in 205 requests; the failure is tracked in #820.
  • Other engines, including WebKit.

Method and gates

  • Sample gate. A run publishes only with at least 200 measured non-warmup requests and zero failures; otherwise the analyzer exits 5. Zero failures in every published cell: each of the four corpus runs has 202 measured requests.
  • Quiet host. A run refuses to start above a 1-minute load of 2.0.
  • Runtime seal. The harness hashes itself, fcvm and fc-agent into a bundle and refuses to measure a golden made under a different bundle.
  • Drift gate. The no-render baseline arm runs through every run. If it drifts, the analyzer rejects the run. Two hugepage passes were rejected this way and discarded.
  • DNS verification. Each corpus run checks the clone’s resolver before and after measuring, samples which process owns port 53 throughout, and requires every query in the replay server’s log to be answered by it (5,306 queries in the 2026-08-30 run). The verdict is written to dns-evidence.json.
  • Replay fidelity. 12 of the 14 sites render identically from the replay; the other two are news sites that differ where ad and consent requests go unanswered.
  • Lints. bench/chromium/test_reqbench.py checks the numbers on this page against the committed records: every ladder figure must be a value from a verified run, withdrawn figures cannot reappear, and Cloudflare’s medians cannot be set against our within-run intervals.

To reproduce the corpus campaign (golden, verification, DNS diagnostics, measured run) from a clean checkout:

make bench-chromium-corpus

The guest vCPU count is part of the golden, so each rung of a ladder needs its own golden. The phase-by-phase targets and knobs are in bench/chromium/AGENTS.md.

Firecracker build

The benchmark uses ejc3/firecracker, branch bump-vsock-max-connections: upstream main as of 2026-02-17 plus four changes.

  • Minor-fault memory backend. Guest RAM is mapped MAP_PRIVATE over a memfd the fcvm memory server passes during the userfaultfd handshake, registered for minor faults. Every minor-mode configuration here depends on it.
  • vsock connection limit raised from 1023 to 16384. Each clone’s status and exec channels use vsock, and a clone per request uses many connections. Fork only.
  • Serial interrupt on restore, a fix plus its regression test. Reported upstream as #5730; upstream fixed it separately in #5764 (2026-03-31), after this base.
  • Dirty-page dump alignment, a snapshot-writing fix. Reported upstream as #5696; upstream shipped its own fix in v1.14.2 (2026-02-27), after this base.

Restored guests need their monotonic clock to continue from the snapshot instant, or every armed timer fires at once. On these plain-EL1 guests the host kernel handles it: since the March 2023 arm64 KVM counter-offset series, KVM recomputes the VM-wide counter offset when a restore replays the saved counter registers. The timer storm fcvm fixed for nested virtualization (#630) needs a virtual-EL2 guest and does not apply to this build.
